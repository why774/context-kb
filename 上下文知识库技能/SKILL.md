# 上下文知识库

平台无关的本地知识库：数据是纯文本目录，任何编辑器能看，任何 AI 能读写。**不依赖任何平台的对话历史。**

核心一句话：

> **原文只留一份，永远在库里；发给 AI 的永远是压缩过的；AI 需要细节时按索引回库里翻。**

---

## 什么时候该加载我

**不是每次都加载。** 这份说明近千行，加载一次就是几百 token。

### 该加载

| 情况                       | 为什么           |
| ------------------------ | ------------- |
| 一场对话已经聊过 20 轮以上          | 上下文吃紧，需要压缩策略  |
| 用户说「上次 / 以前 / 之前说过」      | 要翻旧账（可能要去长期库） |
| 这个项目要被反复改（不止一次）          | 需要跨对话积累       |
| 用户说「记住这个」                | 要落进长期层        |
| 项目里已经有 `.context-kb/` 目录 | 之前用过，继续用      |

### 不该加载

| 情况                 | 为什么       |
| ------------------ | --------- |
| 一次性问答（问个语法、查个 API） | 用不上，加载纯浪费 |
| 第一次碰这个项目、还没建库      | 没有数据可查    |
| 纯闲聊                | 没有要记的东西   |
| 几百行的小脚本、只改一次       | 成本大于收益    |

### 一句话判断

> **这个对话会不会产生"下次还要用到"的东西？**
>
> 会 → 加载。不会 → 别加载。

**加载了就照第五章的顺序做**（铁律 0 是最重要的一条：按顺序做，不要跳步）。

## 30 秒上手

```bash
cd 你的项目目录
python scripts/kb.py log "用户问：改完为什么没生效"   # 第一次 log 自动建这场对话的库
python scripts/kb.py log "答：进程不热加载，要重启" --who AI

python scripts/kb.py seal                    # 这个话题聊完了，封成一段

# 到了「比较近」这一档，AI 一次性把所有段归纳成索引：
python scripts/kb.py index \
  --gist '$重启：ps1 改完必须重启，否则静默不生效' \
  --summary '这条讲的是 ps1 改完不重启就静默失效' \
  --ref "T-20261020-001-p1"

python scripts/kb.py search 不生效           # 下次遇到同样问题

python scripts/kb.py close                   # 结束这场对话
python scripts/kb.py merge                   # 并入长期库（多短都要并）
python scripts/kb.py growth --text "xxx工具要yyy才对"   # 记一条工具经验
```

# 一、核心概念

## 1.1 三层结构

```
热层        长期库的记忆：偏好、铁律、前缀表、长期经验、工具经验
   ↓
检索层      所有索引：一行 = 一个符号 + 一句话结论 + 一个指针
   ↓
原文层      每个索引指向的那段原文（--lines 精确到行）
```

| 层       | 是什么            | 文件                               |
| ------- | -------------- | -------------------------------- |
| **热层**  | 长期库的记忆，跨所有对话累积 | `hot.md`                         |
| **检索层** | 所有索引           | `index.jsonl` + `symbols.jsonl`  |
| **原文层** | 每段原文           | `session/`（进行中）+ `archive/`（已封存） |

**数据从头到尾只有一份。** 分组是「读的时候」发生的，不发生在「写的时候」。

## 1.2 符号 = 组

**前缀就是一个符号。** 一个符号 = 一个组，组里可以有很多条索引，它们前缀都一样。

```
$白名单校验必须前置
↑              ↑
前缀（符号）   结论
```

| 符号  | 组名（说明） | 什么时候用      |
| --- | ------ | ---------- |
| `$` | 代码     | 这条是代码相关的内容 |
| `!` | 坑点     | 踩过的坑       |
| `?` | 疑问     | 还没定论的事     |
| `*` | 关键     | 重要结论       |

**组名只是给人看的说明**（存在前缀表里），检索靠的是符号。

**前缀一定要加**——没前缀就没法被检索到。写索引时忘了挂，程序会拦住你并把表列出来：

```
[ ! ] 这条还没有前缀（前缀一定要加——没前缀就没法被检索到）。
      现有前缀：
        !    坑点         这是踩过的坑
        $    代码         这段是代码相关的内容
      挑一个，写在 gist 开头就行
      没有合适的就新建一个组：kb.py symbol --add "@" --name "待办" --desc "说明"
```

**两个库共用一张前缀表**——长期库那张是权威的，短期库直接读它。这样同一个符号在两边含义一致，合并时才不会打架。

## 1.3 检索：三个坐标

| 坐标 | 命令                     | 按什么            |
| -- | ---------------------- | -------------- |
| 主题 | `search 词`             | 符号/组名 → 列出该组全部 |
| 时间 | `when --since --until` | 日期 → 倒序翻       |
| 段  | `session`              | 对话段落           |

**两跳检索**：先 `search` 拿到 `ref`（段名 + 行号），再 `read` 读那一段原文。

**归属名精确匹配**——搜「白名单」不会命中「白名单校验」。正文内容仍是包含匹配（用户在找内容里的词）。

## 1.4 短期库 / 长期库

**物理上是一个目录，逻辑上分两层。**

|     | 短期库                         | 长期库                    |
| --- | --------------------------- | ---------------------- |
| 是什么 | **这一场对话**的                  | **所有对话**的              |
| 存哪  | `.context-kb/talks/<对话id>/` | `~/.context-kb/`（全局一个） |
| 数量  | 可以多开（一场对话一个）                | 只有一个                   |
| 谁在用 | 当前这场（`context` 按远近分档给它）     | 每场开场都带着（热层）            |

**每开一场对话自动建一个短期库**（`log` 第一次时建），`.context-kb/current` 记着当前是哪场。

**一场对话结束时（`close`），它的成果并入长期层**（`merge`）：

- **只并这场对话产生的**：坑点、偏好、铁律、工具经验、索引、摘要、原文
- **前缀表不并** —— 两边共用，长期库那份是权威的，并进去就有两份了
- **容器不并** —— 只并 `talks/<对话id>/` 这一个子库，`talks/` 上级不动
- **没建索引的段带不走**（没索引 = 搜不到）
- **不管这段对话多短，都要并**

**项目被删时**，用 `unmerge` 把它从长期库踢出去（每条都记了来自哪个项目，踢得干净）。

**长期热层**（`hot.md`）= 长期库的记忆，五块：

```
## 用户偏好        跨所有对话累积
## 长期铁律        跨所有对话累积
## 前缀表          一个符号 = 一个组
## 长期经验        踩过的坑的提炼（从坑点库自动汇总：最近 4 条 + 命中最多 4 条）
## 工具/操作经验    这个工具怎么用才对
```

**搜哪个库**：

```bash
python scripts/kb.py search <词>            # 默认搜短期库（当前这场对话）
python scripts/kb.py search <词> --long     # 搜长期库（跨所有对话）
```

**默认只搜短期库。** 长期库是「别的对话」的东西，只有当用户明确说了要「以前/别的对话/别的项目里的资料」才加 `--long`。**不是每次都两个库都搜。**

## 1.5 压缩分两块：怎么存 · 怎么给

|         | 做什么           | 工具                       |
| ------- | ------------- | ------------------------ |
| **怎么存** | 原文怎么变成索引、摘要   | `log` → `seal` → `index` |
| **怎么给** | 这一次对话给 AI 看多少 | `context`                |

### 怎么存：三级压缩

| 级       | 单位      | 压成什么  | 压缩比   | 什么时候做                    |
| ------- | ------- | ----- | ----- | ------------------------ |
| **原文**  | 1 条消息   | 原文    | 1:1   | `log`（随时）                |
| **段**   | 10~25 条 | 1 条索引 | ≈20:1 | **到「比较近」这一档时**，一次性把所有段归纳 |
| **段摘要** | 1 段     | 1 句话  | ≈10:1 | 同上（跟索引一起做）               |

**原文永远留着**，压缩只是「另存一份简版」。

**压缩和建检索层是同一个动作，在「比较近」这一档开始时做。** 刚开始只堆原文——反正很近的段 AI 看的是全文，不需要索引也不需要摘要。等对话长到要进「比较近」档了，AI 这时一次性把更早的所有段做成索引 + 摘要。

### 怎么给：按远近三档（同一场对话内）

| 档       | 给什么     | 单位   | 参数               |
| ------- | ------- | ---- | ---------------- |
| **很近**  | 原文      | 消息条数 | `--raw-lines 60` |
| **比较近** | 段级摘要    | 段    | `--sum-segs 3`   |
| **比较远** | 索引（带坐标） | 段    | 自动               |

**60 条以内压缩是纯亏**——省的那点 token 不值得，细节没了还得回头再查。**60 条以外只给索引**，不给摘要（摘要比索引还贵，而且没坐标）。

**每一段最终都要有索引**（不是立刻写，是到「比较近」阶段批量补）。理由：没索引 = 搜不到 = 合并到长期库时带不走。

## 1.6 目录结构

```
.context-kb/                    短期库容器（当前目录）
├── current                 记着当前是哪场对话
├── meta.json               编号计数器（全局）
├── symbols.jsonl           前缀表（两边共用，权威那份在长期库）
├── talks/                  各场对话的短期库
│   ├── T-20261020-001/     ← 第一场对话
│   │   ├── session/        进行中的段
│   │   ├── archive/        已封存的段原文
│   │   ├── index.jsonl     段索引
│   │   ├── summaries.jsonl 段级摘要
│   │   ├── hot.md          这场对话的热层
│   │   └── talk.json       这场对话的状态
│   └── T-20261020-002/     ← 第二场对话
└── ...

长期库在别处：~/.context-kb/（全局唯一一个）
```

建议把 `.context-kb/` 提交进 git——这是项目记忆，该跟着代码走。

# 二、归类机制

**核心：AI 只写结论，程序负责归类。AI 不需要想前缀。**

## 2.1 前缀由 AI 定，但只准「点」，不准「想」

前缀是 AI 给的——程序不猜你的意图。问题只在于**怎么让这个动作便宜**。

| 方式               | AI 要做几次 | 成本       |
| ---------------- | ------- | -------- |
| 写完成结论，再回头想"这归哪类" | **2 轮** | 贵，还会反复权衡 |
| 边写边定（`$压缩：结论`）   | **1 轮** | 几乎免费     |
| 单独问"给这段想个前缀"     | 1 轮纯创造  | 最贵，且不一致  |

**关键不在"要不要思考"，在"要不要额外开一轮"。**

### 四个降本措施

**① 清单常驻热层——让它「认」，不让它「想」**

`hot.md` 里一直有前缀表：

```
## 前缀表（写索引时从这里挑；没有就新建一个组）

$ 代码　! 坑点　? 疑问　* 关键
```

有清单，动作就从"**创造**一个前缀"变成"**匹配**一个已有符号"。

**② 先匹配，别追求最优**

> 看到结论 → 扫一眼清单 → 有搭得上的就用 → 没有就新建。**到这儿停。**
>
> 不要做第四步："这个是不是最贴切？"

**③ 格式合并——一行写完，不拆两步**

```bash
--gist '$压缩：headroom 用 CCR 做可逆压缩'
```

**④ 允许先粗后细，错了不致命**

写 `$压缩：xxx` 就行，别一上来追三层。层级后面能加，最坏是多出一个组，`kb.py topic` 一眼看得出来。

## 2.2 词从哪来

### 关键词从「你说的话」里提，不从 AI 的术语里提

| 来源          | 例子                  | 优先级 |
| ----------- | ------------------- | --- |
| **用户原话里的词** | 你说"上下文太长"，就用「上下文太长」 | 最高  |
| 结论里的主体      | "压缩只改请求体" → 「压缩」    | 次之  |
| AI 的技术术语    | "上下文膨胀"             | 最后  |

**用用户的词，不用 AI 的词。** 检索是给人用的——你搜的时候会用自己的说法。

### 写完自测：看「加不增加」和「挤不挤」

```bash
kb.py search 压缩
```

| 看什么                  | 判断             |
| -------------------- | -------------- |
| **这个前缀加不增加**         | 没加 → 前缀没对上，当场改 |
| 加了之后**挤不挤**（条数 vs 线） | 到线 → 该做拥挤测试了   |

**两件事都要 AI 自己判断**，程序不替 AI 决定：

1. **加不加这个前缀** —— 这条内容到底属不属于它。属 → 加；不属 → 换。
2. **要不要新增一层** —— 更挤了就**另起一个新前缀**，别硬塞。

### 什么叫「太挤」

一个前缀下已经 20 条，你塞第 21 条进去。搜它返回 20 条，它排在中后段——**挂进去了，但等于没挂。**

```
[ ! ] 下面这些前缀到预警线了，该做拥挤测试——搜一下看翻起来挤不挤：
   压缩：18 条（线 14）
```

**到线只是预警，不是禁止。** 超过线照样能写。

**分界线按层数递减**（拆得越深说明内容越多、还该再细分）：

| 层    | 系数    | 例子（N=150，基础线 14） |
| ---- | ----- | ---------------- |
| 单前缀  | ×1.0  | 超过 14 条就该拆       |
| 双前缀  | ×0.7  | 超过 9 条就该拆        |
| 三前缀  | ×0.5  | 超过 7 条就该拆        |
| 四层以上 | ×0.35 | 超过 5 条就该拆（下限 5）  |

**基础线为什么夹在 12~20**：库小的时候别太严，库大了顶住，**但不跟库无限涨**——「翻得慢不慢」取决于这一坨有多少条，不取决于库里还有多少别的东西。

**判的是「叶子前缀」的条数**，不是总数、也不是一级前缀：

| 库的样子                              | 该不该报    |
| --------------------------------- | ------- |
| 命中 116 条，分散在 24 个前缀               | 不报      |
| 800 条，一级前缀 800 条但拆成 40 个子主题各 20 条 | 不报（拆够了） |
| 某前缀自己就挂 600 条                     | 报       |

**挤了怎么办**（两条路，程序只报数字，AI 决定走哪条）：

- 内容太杂 → 在原组下细分一层：`symbol --add "新符号" --name "代码/原理"`
- 本来就不该跟原来的一类 → 另起一组：`symbol --add "新符号" --name "新组名"`

## 2.3 前缀表怎么建

```bash
python scripts/kb.py symbol                     # 看表
python scripts/kb.py symbol --add "@" --name "待办" --desc "要做的事"
python scripts/kb.py symbol --remove "$"
```

**写在长期库**（两边共用，权威那份在长期库）。

## 2.4 一条索引可以属于多个组

`--tags` 里可以放别的前缀，这条索引就同时挂在多个组下。

```bash
kb.py index --gist '$白名单：校验必须前置' --tags "白名单校验,open_app" --ref "S-..."
```

搜「白名单」和搜「白名单校验」都能捞到它。

## 2.5 代码怎么进库

**代码有**两套位置\*\*：

| 层                | 放什么             | 样子               |
| ---------------- | --------------- | ---------------- |
| **原文层**（`log`）   | 代码本体，**缩进原样保留** | 包在 \`\`\` 围栏里    |
| **索引层**（`index`） | 从代码里看出的**中文结论** | `$主题：一句话` + tags |

```bash
# 1. 代码照贴，程序自动保缩进
python scripts/kb.py log 'def check_white_list():
    if not ALLOW_LIST:
        return False'

# 2. 索引里写中文结论
python scripts/kb.py index --gist '$白名单：校验必须在 open_app 之前' --ref "S-..." --lines "5-12"
```

**为什么索引里不能放代码原文**：用户搜的是「这段在干什么」，不是变量名。放代码 = 占地方 + 搜不准。

**代码类内容挂 `$` 组**——写在 gist 开头，或用 `--lines` 指到代码那几行让程序自动挂。

**代码里的标识符能搜到**（`search ALLOW_LIST` 命中原文层给你坐标）。但别指望靠搜标识符当主要入口——用户不记得变量名。

# 三、操作流程

## 3.0 调哪个工具（路由表）

### 要查东西

| 情况                   | 命令                                     |
| -------------------- | -------------------------------------- |
| 用户提到「上次 / 以前 / 之前说过」 | `search <用户话里的关键词>`                    |
| 用户要**别的对话**的资料       | `search <词> --long`                    |
| 用户说「按上次那套来」但**没关键词** | **先问，不要查也不要猜**                         |
| 只记得大概时间              | `when --since 2026-10 --until 2026-12` |
| 只记得某一天               | `when --day 2026-10-15`                |
| 时间 × 组交叉             | `when '$' --since 2026-10`             |
| 搜到了索引，想看原文           | `read <坐标>`                            |
| 想看某个组下都挂了什么          | `topic --show <组名>`                    |
| 想看所有组                | `topic`                                |

### 要写东西

| 情况        | 命令                                          |
| --------- | ------------------------------------------- |
| 用户说了一句话   | `log "内容"`                                  |
| 自己给出了结论   | `log "内容" --who AI`                         |
| 一个话题聊完    | `seal` → `index --gist --summary --ref`     |
| 遇到坑       | `pitfall --title --symptom --fix`           |
| 记住用户的偏好   | `pref --text`                               |
| 定一条长期规矩   | `rule --text`                               |
| 记一条工具用法经验 | `growth --text`                             |
| 新建一个组     | `symbol --add "$" --name "代码" --desc "..."` |



### 要维护

| 情况           | 命令                                    |
| ------------ | ------------------------------------- |
| 想知道有没有漏的段    | `check`                               |
| 查某段有没有索引     | `check --ref <段名>`                    |
| 准备一下（可选）     | `init`                                |
| 结束这场对话       | `close`                               |
| 项目结束，成果并入长期库 | `merge`                               |
| 项目被删，从长期库踢出  | `unmerge`                             |
| 看所有库         | `libs`                                |
| 组装给 AI 的上下文  | `context --raw-lines 60 --sum-segs 3` |

## 3.1 准备（可选，不做也能开聊）

```bash
cd 项目目录
python scripts/kb.py init          # 建 talks 容器 + 前缀表（可选）
python scripts/kb.py init --long   # 长期库（全局唯一一个，只需建一次）
```

**短期库不用提前建**——第一次 `log` 会自动建这场对话的库。

`init` 只是把容器和前缀表先准备好，省得第一次 `log` 时才创建。

## 3.2 记原文（对话进行中）

```bash
python scripts/kb.py log "用户说的话"
python scripts/kb.py log "AI 的回答" --who AI
```

**代码贴进去会自动保缩进**（包成围栏），普通文字压成一行。

## 3.3 一个话题聊完：封段 + 写索引

```bash
python scripts/kb.py seal
# → 提示：归纳这一段（用 AI，1-2 条就够）
python scripts/kb.py index \
  --gist '$压缩：headroom 用 CCR 做可逆压缩' \
  --summary '这段讲的是用 CCR 头做可逆压缩，能省一半带宽' \
  --ref "S-20261020-001-p1" --lines "5-40"
```

**也可以封段时顺手写**（`--gist` 只是省一次调用，功能一样）：

```bash
python scripts/kb.py seal --gist '$压缩：headroom 用 CCR 做可逆压缩'
```

**索引是精简到极点的**：一行 = 一个符号 + 一句话结论 + 坐标。

**摘要比索引详细**（索引是一句话，摘要可以是一两句）。

**段内多主题用 `--subs`**，不拆索引：

```bash
--subs "5-40 白名单校验;41-80 启动流程;81-120 异常兜底"
```

## 3.4 写索引的三条细则

### 第 0 步：先跑 `keywords` 定方向，再 `search` 验证

```bash
python scripts/kb.py keywords
```

**AI 不用把内容发过去**——程序自己读当前段文件，AI 只拿结果。

```
S-20261020-001 第 1 段，3 条发言

① 前缀表里的词在这一段里出现过几次（最可靠的依据）：
   $    代码         2 次   → 前缀「$」

② 英文/技术词（技术类话题的前缀通常就是它）：
   bat         5 次

③ 中文高频片段（新话题从这儿挑前缀）：
   中文          3 次
```

**① 最准，②③ 只是参考**（可能出碎片）。拿到候选后走两步：

```
① keywords       → 给方向
      ↓
② 挑一个前缀，search 一次 → 验证
      ↓
   能搜到  → 直接安上
   搜不到  → 新建一个组 → 再 search 一次
```

### ① 代码：原文层原样，索引层写中文结论

见 2.5。

### ② 段内多主题：加小节，不拆索引

见 3.3。

### ③ 命名：`[符号]结论`

见 2.1。

## 3.5 组装上下文（这是出口）

```bash
python scripts/kb.py context --raw-lines 60 --sum-segs 3 --recent 10
```

输出按远近排好：

```
== 热层 · 偏好与铁律 ==
== 很近 · 原文（最近 N 条消息） ==
== 比较近 · 摘要（N 段） ==
== 比较远 · 索引（N 条 · 需要细节就按坐标读原文） ==
== 本地库（可查） ==                 库概况 + 怎么查
```

**没写摘要的段会显示「（还没写摘要）」**。

**段级摘要由 AI 写**，跟索引一起：

```bash
python scripts/kb.py index \
  --gist '$压缩：两者生命周期不同' \
  --summary '厘清了压缩和请求体是两层：压缩属传输层，请求体属应用层' \
  --ref "S-20261020-001-p1"
```

**摘要不另开一条命令**——写索引时顺手就写了，反正 AI 写 gist 时已经理解过这段了。

## 3.6 翻旧账：三段式

```
① 搜（先搜索引，快）
   kb.py search 压缩              # 短期库
   kb.py search 压缩 --long       # 长期库

② 按坐标读原文
   kb.py read archive/S-20261020-001-p1.md:5-40

③ 看整段
   kb.py session S-20261020-001-p1
```

**搜不到再说**——零命中会自动下探原文层。

## 3.7 更长期：偏好与坑点

```bash
python scripts/kb.py pitfall --title "bat中文路径失效" --symptom "改了没生效" --fix "bat正文纯ASCII"
python scripts/kb.py pref --text "喜欢直接说结论"
python scripts/kb.py rule --text "改完必须自己跑一遍"
python scripts/kb.py growth --text "kb.py的log要把代码原样贴，不能压成一行"
```

`rule` 分两种：

- `rule --text` → 长期铁律（跨对话永久有效）
- `rule --text --short` → 本次对话约束（`close` 时自动清出热层，内容留在原文里）

## 3.8 提醒用户：工程里的东西可以自己导入

**别只等用户说「导这个」才导。** 第一次 `log` 建好库之后，或者用户说「记住这个」的时候，AI 主动递一张提醒卡：

> **这个库不只能记聊天。工程里现成的东西，也可以直接导进来：**
>
> | 导什么    | 长什么样         | 命令                                                                  |
> | ------ | ------------ | ------------------------------------------------------------------- |
> | **铁律** | 项目里必须遵守的硬规矩  | `python scripts/kb.py rule --text "..."`                                 |
> | **经验** | 这个工具/操作怎么用才对 | `python scripts/kb.py growth --text "..."`                               |
> | **坑**  | 踩过一次、下次别再踩   | `python scripts/kb.py pitfall --title "..." --symptom "..." --fix "..."` |
> | **偏好** | 你希望我以后都这么干   | `python scripts/kb.py pref --text "..."`                                 |
>
> 不用等我点名；看到工程里有现成的，提醒我一句「要不要导？」就行。

**什么时候提醒**（一次挑一类，别刷屏）：

| 时机                             | 提醒什么                      |
| ------------------------------ | ------------------------- |
| 第一次 `log` 建库后                  | 整张卡                       |
| 项目里有 AGENTS.md / README / 规范文档 | 「里面的硬规矩，要不要用 `rule` 导进来？」 |
| 用户说「记住这个 / 以前说过」               | 「这条我记；工程里的经验、坑也可以一起导」     |
| 对话里出现踩坑复盘                      | 「这条我记成坑点；别的坑也可以自己导」       |

**用户不接话就停**，别追着提醒。**提醒了但用户没明确点头的**，不要自己拍板，按铁律 8 处理：落候选区（`review` → `promote`），等下次一起确认。

**这一节和第 8 条铁律是两条并行的路，互不替代：**

- **铁律 8（AI 自己想加的）**：AI 自己觉得某条东西该长期留下，但用户没提、也没点头 → **先落候选区**，用户确认了才 `promote` 转正；
- **这一节（提醒用户可导入的）**：看到工程里现成的铁律/经验/坑 → **先提醒一句**；用户点头就直接写正式库（`rule` / `growth` / `pitfall`）。

两者都是 AI 主动开口，区别只在于：一个先放候选区等 review，一个当场问一句、点头就写。

## 3.9 清理与删除

```bash
python scripts/kb.py gc          # 检查超期 + 重复（不加 --apply 不动手）
python scripts/kb.py rm <key>    # 删除（不加 --yes 只列清单）
python scripts/kb.py review      # 看待审条目
```

**清理只提醒，不替用户做主：**

- `gc` / `rm` 都是**先给清单**；AI 的活是把清单翻译成人话：**“这些条目已经多久没被用到（`last` 太旧、`hit` 一直为 0）、这两条疑似重复——你看要不要处理”**；
- **等用户看完拍板**：用户说“删”才删；用户没表态就只提醒，**不要自己加 `--apply` / `--yes`**；
- **长期库不主动删**：只有用户明确要求删哪条，才 `rm <key> --yes`；`gc --apply` 也只是把超期条目标成 `archived`（可恢复，不是删除）；
- 判断“很久没用到”就看 `last`（最后被踩/记录时间）和 `hit`（被检索命中次数），`gc` 的阈值是 180 天；这两个数**不用人记**——`search` / `when` 真把一条坑点翻出来看过，程序就自动给它 `hit`+1、`last` 刷成当天。

# 五、十七条铁律

## 铁律 0（最重要）：**按顺序做，不要跳步**

**这 17 条不是并列的清单，是一条有先后依赖的链。跳步 = 全盘皆输。**

**唯一的分界点是「比较近」这一档**——在那之前只堆原文，之后才开始建检索层。

```
① 每轮      log --who AI                           记原文（每轮至少一条）
   ↓                                                 第一次 log 自动建这场对话的库
② 话题完    seal                                   封段
   ↓
   ══════ 到这里为止，只堆原文，不写索引 ══════
   ↓
③【触发点】对话长到要进「比较近」档
   ↓         keywords → index                       压缩 + 建检索层（同一个动作）
   ↓                                                 ← 这时才真正「建库」
④ 验证      search                                 看加不增加、挤不挤
   ↓
⑤ 挤了      symbol --add                           新建一个组
   ↓
⑥ 组装      context                                每轮发给 AI 之前
   ↓
⑦ 结束      close → merge → growth                 并库 + 记经验
```

**第 ③ 步之前，一条索引都不用写。** 反正很近的段 AI 看的是全文。

**`init` 不是铁律**——它只是可选的准备动作（建 `talks/` 容器 + 前缀表）。


第一次 `log` 会自动建这场对话的库，**不 `init` 也能直接开聊**。

# 六、反模式

| 别做              | 为什么                   |
| --------------- | --------------------- |
| 一次 `log` 塞一大段   | 段太大，切不出「问题闭环」         |
| 一个索引写五六个前缀      | 筛选失效，每条都「一半相关」        |
| 索引里贴代码原文        | 占地方 + 搜不准             |
| 主题名用 AI 的术语     | 用户不会用你的术语搜            |
| 库建在临时目录         | 换个地方就找不到了             |
| 不写 `--lines`    | 索引指向整段，回看时分不清是哪儿      |
| 每次都搜长期库         | 长期库是「别的对话」的东西，混在一起反而乱 |
| 为了「完整」把原文全塞给 AI | 60 条以内压缩是纯亏，细节该留原文    |

# 七、这玩意儿有成本

| 项            | 成本                        |
| ------------ | ------------------------- |
| 加载这份说明       | 几百 token（所以不是每次都加载）       |
| `log` 一次     | 几乎为零                      |
| `index` 一次   | AI 要想一次前缀（可以从清单点，成本≈0）    |
| `search` 一次  | 毫秒级，零 token               |
| `context` 一次 | 输出几百到两千 token（就是给 AI 的那份） |
| 磁盘           | 纯文本，几十 KB 起               |

**热层是每轮都会带上的那份**（`hot` 看内容）。别往里塞细节——细节去坑点库。

**长期库会越来越大**——`gc` 定期查超期的坑点，**只提醒用户哪些很久没用到**，由用户看完再决定，**不自动删**。
